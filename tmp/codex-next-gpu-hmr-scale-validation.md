## Important Pipeline Risk To Investigate

Inspect the full file handoff into the AI GPU splitter. A realistic project will
not be a single `main.cpp`; kernel engineers often keep device code in separate
`.hip` or `.cu` files with headers and host launch code elsewhere.

The current worker split code in
`backend/synthi-webrtc-compiler/worker/src/compiler/stages/ai_utils.rs` builds
the AI payload mostly like this:

```text
code = req.source
lang = req.language
```

It detects GPU markers across `req.files`, but confirm whether it actually sends
the full `req.files` list to ai-engine `/refactor/split/gpu`. The ai-engine
endpoint already has request-file support:

```text
ai-backend/ai-engine/main.py
  VerifiedAiRequest.files
  _file_map_from_request
  /refactor/split/gpu
```

If the worker is only sending the active source string, multi-file GPU projects
will fail or the model will hallucinate missing context. Fix that before
claiming the pipeline supports real projects.

Also inspect the MCP harness. At the time of this handoff,
`mcp/synthi-mcp/scripts/gpu-hmr-agent-split-workspace-test.mjs` calls
`synthi_compile` for the first split with:

```text
filename: main.cpp
source: <monolithic source>
files: []
```

That is not adequate for a scale test. Create or extend a harness that sends a
large project file set through MCP.

## Required Scale Test

Create a GPU HMR validation project with hundreds of files. It should include:

- Multiple nested source directories.
- Real host source files: `.cpp` and `.hpp`.
- Device source files: `.hip` on ROCm and/or `.cu` on CUDA.
- Kernel declarations split from kernel implementation.
- Host-side launch or simulation code separate from rendering code.
- Decoy files that should not affect compile.
- Nonstandard filenames and directories.
- No user-authored Synthi ABI exports.

Minimum expected shape:

```text
src/app/main.cpp
src/app/simulation.cpp
src/app/simulation.hpp
src/render/render_backend.cpp
src/render/render_backend.hpp
src/gpu/particles.hip
src/gpu/particles.hpp
src/math/*.hpp
src/config/*.hpp
assets_or_docs_or_decoys/... many files ...
```

The model should receive enough context to split this into the generated Synthi
runtime roles. The generated roles may still be the current C++ GPU HMR
contract, but the user project itself must not be forced into those filenames.

## Hardcoding Rules

Do not introduce SDL2-only generation. SDL2 can be one fixture backend, not the
product contract.

Allowed stable contract:

- Synthi ABI export names used by the runner.
- `synthi_gpu_runtime.h` as the runtime boundary between generated host code
  and the GPU sidecar loader.
- Current generated role concept for C++ GPU HMR.

Not allowed:

- Requiring user files to be named `core.cpp`, `gui.cpp`, `host_runner.cpp`, or
  `device.hip`.
- Requiring user source to contain Synthi ABI exports.
- Assuming SDL2 when the user used another rendering backend.
- Recovering render surfaces through hardcoded global IDs or implicit lookups.
- Testing only a pre-split workspace and calling that full user validation.

Verifier checks in `ai-backend/ai-engine/verifier_gpu.py` are guardrails for
bad generated output. Some checks may reject known bad SDL2 anti-patterns, but
that does not mean the splitter should translate everything to SDL2.
