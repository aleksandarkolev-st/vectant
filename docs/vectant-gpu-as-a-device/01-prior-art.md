# Prior Art Forensics: Why Transparent Remote GPU Attachment Has Never Shipped

**Scope.** Forensic review of the relevant known prior art attempting to make a remote or pooled physical GPU usable by an *unmodified application on the user's own machine* — the Vectant goal (`vectant rent rtx5090 --hours 2` → local apps see a second GPU). For each system: mechanism, transparency level, what worked, measured overheads, why it missed the goal, and the transferable lesson.

---

## 1. Academic Lineage

### vCUDA (2009–2012, Shi et al., NUDT/WSU)
Mechanism: intercepts CUDA calls inside a VM via interposition at the CUDA runtime layer; API state is mirrored to a "shadow" device so a migrated VM can rebind to another physical GPU ([IPDPS'09](https://www.computer.org/csdl/journal/tc/2012/06/ttc2012060804/13rRUwInuVO)). Transparency: **relink/LD_PRELOAD-class interception** of the CUDA runtime, deployed *inside VMs*. Overhead: vmCUDA-era measurements showed **0.6–3.5% overhead for applications** on cluster interconnects ([Academia copy](https://www.academia.edu/79213645/Improving_the_user_experience_of_the_rCUDA_remote_GPU_virtualization_framework)). Why not Vectant: built for VMs, not bare-metal end-user machines, and never handled graphics APIs; interception surface was the runtime, not the driver model. Lesson: mirroring device state enables *migration* and *pooling* — exactly the remote-state residency principle Vectant needs.

### rCUDA (2010–2023, UPV/UJI — Duato, Silla, Mayo, Quintana-Ortí)
The most mature transparent CUDA remoting system ever shipped. Mechanism: replaces `libcuda` on the client with an intercepting middleware that forwards the ~600-call CUDA Driver API over TCP/IB/RoCE to a server daemon owning the real GPU; all allocations live in remote VRAM ([UPC paper](https://upcommons.upc.edu/bitstreams/f4f74b94-3d2c-41d8-8dae-98c1d0e80b5b/download), [rCUDA site](https://rcuda.io/)). Transparency: **library replacement** — unmodified binaries run, but only because Linux lets you swap `libcuda.so`. Measured results: negligible overhead over InfiniBand FDR/EDR ("local and remote GPUs perform similar" with EDR 100G — [ACM/ICPE](https://dl.acm.org/doi/10.1145/2830013.2830015)); over plain Ethernet, performance collapses proportional to dataset size ([IEEE 6702662](https://ieeexplore.ieee.org/document/6702662)); later work added pipelined compression for edge/WAN links ([SC'22](https://dl.acm.org/doi/10.1145/3547276.3548628)) and job migration across heterogeneous GPUs ([IEEE TD'19](https://www.computer.org/csdl/journal/td/2019/12/08744256/1eTOMLM8rvO)). Adoption stalled because: (a) Linux-only library swap breaks on Windows/macOS where `nvcuda.dll`/driver signing resist substitution; (b) HPC-focused — assumes trusted cluster LAN, no multi-tenant auth/billing; (c) CUDA-only, zero graphics; (d) every synchronous CUDA call is a network round trip, so latency-sensitive and sync-heavy workloads crater off-InfiniBand; (e) academic maintenance cadence vs. NVIDIA breaking ABI each driver release. Lesson: full-API replay works when bandwidth is high and sync density low — Vectant's data plane is essentially rCUDA's protocol problem plus consumer-network reality plus Windows.

### gVirtuS (2009–present, NVIDIA/CNR then open source)
Mechanism: split-component framework — a "front-end" intercepts CUDA/OpenCL calls and marshals them to a "back-end" executing against the real driver, communicating over TCP or shared memory ([Euro-Par'10](https://pure.qub.ac.uk/files/90703373/gvirtusarm_20160904.pdf), [repo](https://github.com/NVIDIA/gvirtus)). Transparency: LD_PRELOAD front-end. Recent work extends it to ARM/x86 remoting and LLM serving (GVirtuS delivers up to ~2× speed-up for LLM inference vs CPU-only — [AAU/vbn abstract](https://vbn.aau.dk/en/publications/computational-resources-for-llm-computing-the-need-for-gpu-virtua/); Aalborg students benchmarked its remote-mode overheads [here](https://projekter.aau.dk/projekter/files/841357045/CE_2_GRP3_Semester_Project_2.pdf)). Why not Vectant: same class as rCUDA (Linux interception, compute-only, no session/commerce layer), historically fragile across CUDA versions. Lesson: the interceptor/back-end split is the right shape for a control-plane/data-plane separation; gVirtuS proves the plumbing survives 15 years of CUDA churn only with constant codegen-style upkeep.

### DS-CUDA (2012, Keio/UEC — Kawai, Yasuoka, Yoshikawa, Narumi)
Mechanism: virtualizes a 22-node/64-GPU TSUBAME 2.0 slice into "a single PC with many GPUs," adding redundant-execution error recovery for non-ECC GeForce cards ([FUTURE COMPUTING'12](https://www.thinkmind.org/download.php?articleid=future_computing_2012_1_20_30069), [IEEE](https://ieeexplore.ieee.org/document/6495928)). Transparency: source-code-level global view; requires program awareness of the distributed runtime. Why not Vectant: explicitly *not* transparent — targets MPI-era cluster users; reliability-by-redundancy triples network traffic. Lessons: (1) consumer GPUs without ECC will corrupt remote sessions — Vectant needs error detection at session scope; (2) "many GPUs behind one API" is a different product than "one GPU behind one app."

### CuVA / Carbon (Tel Aviv University, ~2014–2016)
CuVA proposed coherence-based virtualization of CUDA address spaces so multiple guests share one physical GPU with per-guest address-space isolation (hardware/IVSHMEM-assisted rather than pure software replay); Carbon extended the group's remote-computing line toward streaming execution from mobile devices to server clusters. Both remained laboratory prototypes with limited public artifacts; searches surface them mainly through citation trails ([ACM address-space formalization](https://dl.acm.org/doi/10.1145/2458523.2458527), survey coverage in [Hessar et al. context](https://hal.science/hal-05429292v1/document)). Why not Vectant: no shipped artifact, no WAN story. Lesson: address-space-level virtualization (rather than call replay) is the only route that preserves pointer semantics for UVA programs — a real constraint Vectant inherits, since torch/cuBLAS assume one unified address space.

### GPUrpc / Gdev (2016, Iida et al., KEIO/U.Tokyo — Kato group)
Mechanism: RPC extension of Gdev (user-space-first-class GPU management) so *every* CUDA API becomes a remote call ([ACM TECS](https://dl.acm.org/doi/10.1145/2950056)). Transparency: full CUDA surface via custom runtime. Finding: naive per-API RPC is reliable but slow — confirming that RPC-per-call designs live or die on batching. Lesson: the field already concluded in 2016 that transparent = possible, fast = must batch; nobody productized the second half on WANs.

### Surveys (the consensus view)
[Hessar & Nazari, ACM CSUR 2017](https://dl.acm.org/doi/10.1145/3068281) taxonomize API remoting vs. passthrough vs. hardware partitioning; the 2025 [comprehensive review](https://hal.science/hal-05429292v1/document) and [Future Computing benchmarks](https://www.sciencedirect.com/science/article/pii/S0167739X25002390) still conclude mediated-passthrough dominates production because API remoting degrades under latency. [GPU-Virt-Bench (2025)](https://arxiv.org/pdf/2512.22125) now benchmarks software virtualizers systematically. Consensus lesson: every transparent system pays at the synchronization boundary; every non-transparent one demands relocation of the workload.

### Disaggregated-memory systems (latency/batching canon)
- **Infiniswap (NSDI'17)**: remote memory as block-level paging with demand paging, opportunistic locality-aware slab placement, and *batched* RDMA fetches; hides most of the ~µs RTT ([paper](https://www.usenix.org/system/files/conference/nsdi17/nsdi17-gu.pdf)). Lesson: never expose raw round trips — multiplex many logical accesses into few network ops.
- **Semeru (OSDI'20)**: language-runtime-managed remote memory keeps the *hot* heap local and pushes cold objects remote; co-designs collector with network ([paper](http://web.cs.ucla.edu/~harryxu/papers/wang-osdi20.pdf)). Lesson: place state by access temperature — Vectant should pin hot weights/textures remotely and stream only deltas.
- **LegoOS (OSDI'18)**: splits kernel components across network-attached monitors; global virtual address space with distributed page caching ([USENIX](https://www.usenix.org/conference/osdi18/presentation/shan), [repo](https://github.com/Wuklab/LegoOS)). Lesson: a small "monitor" layer owning naming+placement makes heterogeneous pools look like one machine — a template for Vectant's host service.
- **Galaxy/GCMP-class cache-coherent GPU memory pools**: catalogued in the 2025 cross-layer survey ([arXiv 2503.20275](https://arxiv.org/html/2503.20275v1)) alongside Samsung's CMM results showing near-DRAM behavior for pooled memory in inference backends ([Samsung tech blog](https://semiconductor.samsung.com/news-events/tech-blog/breaking-ai-memory-limits-with-cxl-memory-pooling/)). Lesson: cache-coherent fabrics change the game from "batch everything" to "let hardware handle fine grain" — but only within a rack.

## 2. Industry Attempts

### VMware Bitfusion (2016–2023)
Mechanism: intercepts CUDA at the API level on the client ("Boost"/client component), ships the calls + tensor payloads to servers holding physical GPUs pooled across vSphere; presented to apps as ordinary CUDA ([The Next Platform deep-dive](https://www.nextplatform.com/ai/2016/10/11/ganging-up-accelerators-to-beat-scale-limits/1638517), [field walkthrough](https://linuxpunx.com/2018/10/04/using-gpus-with-virtual-machines-on-vsphere-part-4-working-with-bitfusion/)). Transparency: client-side interception agent; apps unmodified, but officially supported only *inside* vSphere VMs. What worked: partial-GPU allocation, pooling across racks, real ML training over 10–40GbE. Why VMware killed it: **End of Availability May 5, 2023** with Broadcom's acquisition ([Broadcom KB 322267](https://knowledge.broadcom.com/external/article/322267/end-of-availability-eoa-for-vsphere-bitf.html), support ended May 2025 — [KB 322304](https://knowledge.broadcom.com/external/article/322304/vsphere-bitfusion-support-guide.html)). Root causes visible in the record: tied to expensive vSphere licensing; NVIDIA's MIG made in-server slicing cheaper than network remoting; and the client had to be a managed VM, never the developer's own desktop. Lesson: the technology worked; the *deployment envelope* (enterprise hypervisor, LAN-only) was the ceiling. Vectant differs precisely by targeting the user's existing machine over the internet.

### NVIDIA vGPU / vCompute Server / MIG
Mechanism: vGPU = hypervisor-hosted paravirtual device backed by host driver timeslicing (requires VM + licensing — [user guide](https://docs.nvidia.com/grid/14.0/grid-vgpu-user-guide)); MIG = hardware partitioning of Ampere+ GPUs into up to 7 isolated instances ([concepts](https://docs.nvidia.com/datacenter/tesla/mig-user-guide/concepts.html), [overview](https://www.nvidia.com/en-us/technologies/multi-instance-gpu/)); MIG-backed vGPU composes both ([NVIDIA AI Enterprise docs](https://docs.nvidia.com/ai-enterprise/release-8/latest/infra-software/vgpu/features/mig-backed-vgpu.html)). Open-source KVM ports still require supported products and licenses ([Proxmox thread](https://www.reddit.com/r/Proxmox/comments/1fphprl/vgpu_going_open_source/)). Why not Vectant: all three move the *workload* into a VM on the GPU's host — the exact anti-goal; nothing attaches to a user's local OS. Lesson: NVIDIA's roadmap monetizes consolidation inside the server, leaving the client-attachment quadrant empty — the strategic gap Vectant occupies.

### GPUDirect RDMA / Storage
Mechanism: PCIe peer DMA between NIC/NVMe and GPU framebuffer, bypassing CPU bounce buffers ([docs](https://docs.nvidia.com/ai-enterprise/release-8/latest/infra-software/vgpu/features/gpudirect.html), [benchmark blog](https://forums.developer.nvidia.com/t/benchmarking-gpudirect-rdma-on-modern-server-platforms/148424)). Solves microsecond-to-millisecond transfer classes *within one host*. Why not Vectant: it optimizes the wrong hop — it removes the CPU from local transfers but cannot span a WAN; still, it defines the latency floor Vectant competes against (~1–2 µs intra-host vs. 100 µs–30 ms WAN RTT, a 10³–10⁴× gap that motivates every batching design). Lesson: Vectant's data plane should terminate RDMA-class paths at the host daemon and treat the WAN as a separate, batched channel.

### ZLUDA (API-translation precedent)
Mechanism: drop-in replacement of CUDA libraries translating PTX/SASS execution onto AMD HIP/ROCm — proof that stock CUDA applications can run on non-NVIDIA silicon without rebuilds ([project](https://zluda.org), [HN discussion](https://news.ycombinator.com/item?id=39604745)). Fallout: originally funded by AMD, defunded in 2024; AMD forced author Andrzej Janik to rebuild the paid-for code from a pre-AMD base over legal concerns; repos were taken down Aug 2024 ([Phoronix](https://www.phoronix.com/news/AMD-ZLUDA-CUDA-Taken-Down), [The Register](https://www.theregister.com/software/2024/08/09/amd-lawyers-claw-back-cuda-compatibility-layer-zluda/1009658), [Tom's Hardware](https://www.tomshardware.com/pc-components/gpu-drivers/cuda-emulator-for-amd-gpus-zluda-loses-funding-with-v6-release-embattled-project-goes-back-to-hobby-status-but-now-includes-32-bit-physx-support)); drivers reportedly use EULA restrictions to block compatibility layers ([HardForum quote](https://hardforum.com/threads/zluda-allows-cuda-binaries-to-run-on-amd-gpus.2033326)). Why relevant: ZLUDA demonstrates binary-level CUDA transparency is achievable *and* that the legal surface (CUDA EULA, driver license terms) is the hardest constraint — directly applicable to any Vectant component that reimplements or forwards CUDA interfaces. Lesson: prefer forwarding *calls to genuine drivers* (like rCUDA/Bitfusion) over reimplementing the API (ZLUDA) to stay clear of license landmines.

### Mesa VirGL / virtio-gpu Venus / Android gfxstream
Mechanism: guest GL/Vulkan calls are serialized over virtio ring buffers to a host renderer (virglrenderer/Venus = Vulkan command serialization — [Mesa Venus docs](https://docs.mesa3d.org/drivers/venus.html), [QEMU docs](https://www.qemu.org/docs/master/system/devices/virtio/virtio-gpu.html)); gfxstream generalizes this to "from one computer to another via network" with resource sharing ([gfxstream repo](https://github.com/google/gfxstream), [Cuttlefish docs](https://source.android.com/docs/devices/cuttlefish/gpu)). Transparency: guest sees standard APIs through paravirtual drivers — but requires guest kernel modules and a cooperating hypervisor/host. What transfers to WAN: the *protocol* (command serialization with persistent host-side resources, dmabuf-style opaque handles, fence-based sync) is exactly right; Venus even relies on shared-memory mappings for host-visible allocations ([Venus host-visible notes](https://docs.mesa3d.org/drivers/venus.html#vk-memory-property-host-visible-bit)), which a WAN system must replace with explicit ownership transfer. Lesson: the graphics stack already invented Vectant's wire protocol — locally. Nobody has run it over a routed network with auth/billing; gfxstream's stated "computer to computer" mode is the nearest neighbor.

### Windows WSL `/dev/dxg`
Mechanism: Microsoft projects the WDDM interface as a set of IOCTLs over Hyper-V VMBus; the Linux `dxgkrnl` creates `/dev/dxg`, matching D3DKMT, letting D3D12/DirectML/CUDA run in a Linux VM sharing the Windows host GPU ([LWN patch cover letter](https://lwn.net/Articles/820950/), [architecture deck](https://lpc.events/event/9/contributions/610/attachments/700/1295/XDC_-_WSL_Graphics_Architecture.pdf), [Microsoft blog](https://devblogs.microsoft.com/directx/directx-heart-linux/)). Key details: video memory lives on the host; CPU-visible allocations are mapped into an 8 GB IO-space window; no display path exposed — rendering/compute only. Layering template: *API projection → IOCTL channel → host allocator + scheduler*, i.e., a clean seam where a network transport could replace VMBus. Why not Vectant: transport is a hypercall bus inside one machine; Windows client + Windows host only. Lesson: the WDDM IOCTL surface is the natural interception point for DirectX on Windows clients — more stable than hooking `dxgi.dll`, and Microsoft itself maintains the semantic mapping.

### CXL Type-2 GPU pooling (Panmnesia, Samsung CMM, Liqid)
Mechanism: attach GPU memory (or whole accelerators) via CXL controllers with two-digit-nanosecond latency, presenting pooled DRAM/SSD as coherent GPU-attached storage ([Panmnesia CXL-GPU whitepaper](https://panmnesia.com/uploads/panmnesia-CXL-GPU.pdf), [Panmnesia blog](https://panmnesia.com/technology/blog/2024-06-25-cxl-gpu-techblog/), [Samsung CMM](https://semiconductor.samsung.com/news-events/tech-blog/breaking-ai-memory-limits-with-cxl-memory-pooling/), [Liqid pooling](https://www.liqid.com/products/memory-pooling-solutions)); CXL 4.0 doubles link speeds again ([industry explainer](https://introl.com/blog/cxl-4-0-infrastructure-planning-guide-memory-pooling-2025)). What changes vs IP: latency drops from milliseconds to hundreds of nanoseconds and coherence becomes hardware-enforced, so fine-grained pointer-chasing works — no batching needed; but reach is meters (single rack, switch hops), not kilometers. Why not Vectant: CXL cannot deliver a GPU to a home/office over the internet; it solves pooling *inside* the datacenter Vectant rents from. Lesson: Vectant hosts should exploit CXL internally for VRAM expansion/pooling while the WAN edge still uses API-replay semantics.

## 3. Cloud Gaming: The Opposite Point on the Tradeoff Axis

**Where they put state:** everything remote. GeForce NOW runs the entire game (CPU state, assets, GPU) in datacenters and streams pixels ([NVIDIA overview](https://blogs.nvidia.com/blog/what-is-cloud-gaming)); Stadia/xCloud identical in outline, differing in transport (RTP/UDP flows analyzed in [MDPI network study](https://www.mdpi.com/2673-8732/1/3/15)); Steam Remote Play instead captures/encodes on a *user's* host using NvFBC capture + NVENC encode ([community technical breakdown](https://steamcommunity.com/groups/homestream/discussions/0/451850849186356998/)).

**Why pixels, not API calls:** the interaction loop tolerates one frame of latency but not thousands of synchronized API round trips; encoding one 60 fps video stream costs far less bandwidth than replaying draw calls, and it preserves DRM (the game never leaves the cloud — a commercial reason API-replay can't serve publishers).

**Published hybrid techniques:**
- **Negative latency / speculative input** — Stadia's publicized plan: run frames before inputs arrive and rewind when predictions miss ([coverage of Stadia engineering](https://prosyscom.tech/gaming-news/googles-apparent-plan-to-tackle-lag-on-stadia-explained)).
- **Outatime (UW/Microsoft, MobiSys'15)**: speculate ~16 future frames per input event on phones, correct on arrival — proven 4× latency reduction ([paper](https://dl.acm.org/doi/10.1145/2742647.2742656), [slides](https://cs.princeton.edu/courses/archive/fall15/cos518/studpres/outatime.pdf)).
- **Late input latch / post-render warp** — NVIDIA's Latewarp resamples the camera transform after render to hide queue/network delay ([HPG'20](https://research.nvidia.com/sites/default/files/pubs/2020-07_Post-Render-Warp-with/HPG_2020_Latewarp_AuthorVersion_0.pdf)).
- **Split rendering** — distributing render work between client and cloud GPU ([hybrid-streaming method, IJSG](https://journal.seriousgamessociety.org/index.php/IJSG/article/download/163/pdf_89/825), [SFU MMSys'25 decoupled upscaling](https://www.cs.sfu.ca/~mhefeeda/Papers/mmsys25_transparentSR.pdf)).

Why none achieve the Vectant goal: all keep the *application* remote by construction; the client is a decoder. But their latency arsenal (speculation, warp, prediction) transfers directly to Vectant's thin-command channel for interactive workloads.

## 4. Novel Systems 2023–2026

### Genie / "Lost in Translation" (UC Berkeley, HotNets'25)
Mechanism: argues low-level disaggregation (PCIe/driver-call replay) is "semantically blind" — a shim "cannot identify the difference between an LLM's prefill phase … and decode phase" — and proposes the framework layer as the narrow waist with a semantically-rich graph deferring execution ([HotNets'25 paper](https://conferences.sigcomm.org/hotnets/2025/papers/hotnets25-final8.pdf)). Transparency: none at the app level (framework-mediated). Why not Vectant: requires framework cooperation — violating Vectant's no-app-change rule. Lesson: confirms the industry diagnosis — pure lower-layer replay strands performance knowledge; Vectant must recover phase/residency hints *heuristically* (allocation lifetimes, kernel recurrence) since it cannot demand SDK cooperation. Also documents fleets idle **55–60%** of GPUs — Vectant's market thesis.

### LUPINE — GPU-over-IP (lupinemachines, 2024–active Aug 2026) ⚠️ closest prior art
Mechanism: open-source bridge attaching remote GPUs to CPU-only machines: client implements the CUDA driver surface (libcuda-level, driver-API focus per commit history: ["libcuda driver-only based api"](https://github.com/lupinemachines/lupine/commit/18e324ec48ae8c527a86d003a7003e130b69d615)), server executes on the real GPU; demo shows `nvidia-smi -L` listing a Tesla T4 "(via lupine demo.lupinemachines.com)" and a Mac running PyTorch with `cuda available: True` against a remote RTX 4090 ([README](https://github.com/lupinemachines/lupine), [third-party profile](https://hysenlabs.com/en/projects/lupinemachines-lupine); 2.4k stars, Apache-2.0). This is functionally the Vectant milestone (unmodified torch, remote silicon, `torch.cuda.is_available()==True`). Gaps vs Vectant: Linux containers first (Windows/macOS via container escape hatch, not native driver integration); no commerce/control plane beyond a demo endpoint; no published WAN benchmark suite; single-operator. Lesson: existence proof that the hard part (driver-API fidelity incl. mapped-memory RPC — recent commits optimize "mapped-memory RPC reads") is tractable by a small team; Vectant's differentiation must be the *product shell*: Windows-native attachment, session lifecycle, routing, billing, SLAs.

### iFrame (neocloud operator tooling, Nov 2025)
Mechanism: CLI mounting remote GPUs "as if physically attached to the local CPU machine via the PCIe bus," building on the company's Sept 2022 disclosure of PCIe-over-TCP/IP virtualization; positions packetization/latency mitigation as solved at infrastructure layer ([ComputingForGeeks report](https://computingforgeeks.com/iframe-ships-gpu-virtualization-cli-for-neocloud-operators), vendor: [iframe.ai](https://www.iframe.ai/)). Transparency: claims device-level (PCIe) illusion for operators' CPU machines. Caveats: marketing-grade evidence, no independent benchmarks, aimed at B2B neocloud fleets rather than consumer desktops. Lesson: commercial momentum exists in exactly Vectant's direction; the "PCIe-over-TCP" claim mirrors NEC ExpEther (below) — treat device-bus emulation over WAN as plausible-but-unproven until benchmarked.

### DxPU (Alibaba, arXiv 2023)
Mechanism: datacenter-scale GPU disaggregation pooling GPUs behind dedicated gateways with a lightweight protocol, flexibly allocating GPUs to CPU nodes ([DxPU paper](https://arxiv.org/pdf/2310.04648v1)). Scope: intra-datacenter, rack-scale fabric — complements NSDI'25's GPU-disaggregated recommendation serving ([NSDI'25](https://www.usenix.org/conference/nsdi25)) which moved KV/embedding states across hosts. Lesson: hyperscalers are rebuilding their fleets around detachable GPUs — supply-side precedent Vectant can ride (rent slices of such pools), though none expose anything outside their fabric.

### NEC ExpEther (PCIe-over-Ethernet, long-running, demoed Gen3 x16 over 100GbE)
Mechanism: transports actual PCIe transactions over Ethernet so GPUs/NVMe appear on a remote chassis's bus ([2025 demo coverage](https://armdevices.net/2025/12/26/nec-expether-pcie-over-ethernet-demo-gen3-x16-over-100gbe-fiber-gpu-pooling)). Transparency: true bus level — no software changes at all. Constraints: requires LAN-latency, lossless-ish links and special adapters; unusable across the internet (PCIe timeouts fire at microsecond scales). Lesson: bus transparency and WAN are fundamentally incompatible at today's latencies — any Vectant design must give up bus-level fidelity in favor of protocol-level (API) fidelity with timeout forgiveness.

## 5. Synthesis

### (a) Five fundamental reasons transparent local-app remote GPU attachment never shipped

1. **The latency asymmetry is structural.** Local GPU interactions run at 10¹–10³ events/ms with sub-microsecond service; WAN RTTs are 10²–10⁴ µs. Every transparent system (rCUDA, Bitfusion, GPUrpc) degrades proportionally to synchronization density; only high-bandwidth RDMA LANs hide it, which is why success stayed inside datacenters ([EDR study](https://dl.acm.org/doi/10.1145/2830013.2830015), [Ethernet degradation](https://ieeexplore.ieee.org/document/6702662)).
2. **No stable, portable interception point exists below the API.** GPUs lack a standard device interface (noted since rCUDA's founding papers — [UPC](https://upcommons.upc.edu/bitstreams/f4f74b94-3d2c-41d8-8dae-98c1d0e80b5b/download)); bus-level emulators die at microsecond PCIe timeouts (ExpEther), and driver-model hooks (dxgkrnl, virio-gpu) require kernel cooperation from the host OS vendor. So everyone lands on library interception — which Windows signing, macOS SIP, and anticheat ecosystems actively resist.
3. **Pointer/address-space assumptions break across the network.** Unified addressing means the app treats CPU and GPU pointers interchangeably; remote VRAM invalidates that unless the whole address space is virtualized (CuVA's unsolved-in-practice problem — [formalization](https://dl.acm.org/doi/10.1145/2458523.2458527)). Mapped memory, pinned transfers, and zero-copy idioms all become round trips.
4. **The economics rewarded consolidation, not attachment.** NVIDIA monetized putting workloads *in* server VMs (vGPU/MIG — [docs](https://docs.nvidia.com/datacenter/tesla/mig-user-guide/concepts.html)); enterprises bought that; Bitfusion died commercially despite working tech ([EOA notice](https://knowledge.broadcom.com/external/article/322267/end-of-availability-eoa-for-vsphere-bitf.html)). No incumbent had incentive to solve client attachment.
5. **Legal/licensing moats guard the CUDA surface.** ZLUDA's takedown shows API reimplementations face existential legal risk ([Phoronix](https://www.phoronix.com/news/AMD-ZLUDA-CUDA-Taken-Down)); driver EULAs restrict interposition; and cloud gaming proved the DRM-friendly alternative (keep the app server-side). Transparent attachment threatens both license structures simultaneously.

### (b) Untried combinations that look most promising

1. **rCUDA/gVirtuS protocol fidelity × dxgkrnl-style WDDM IOCTL projection on Windows.** Project the *vendor IOCTL surface* (stable, documented semantics) instead of hooking user DLLs, then forward those commands over a direct client↔host connection. Nobody has combined the two.
2. **Persistent-state residency (Vectant's stated principle) × Semeru-style temperature-based placement.** Pin weights/assets remotely at init; classify per-buffer heat at runtime; migrate only cold↔hot boundaries. rCUDA moves everything per call; no system does thermal-state-aware residency over WAN.
3. **Batching + speculation from cloud gaming applied to compute channels.** Outatime-style speculation and Latewarp exist only for pixels ([Outatime](https://dl.acm.org/doi/10.1145/2742647.2742656), [Latewarp](https://research.nvidia.com/sites/default/files/pubs/2020-07_Post-Render-Warp-with/HPG_2020_Latewarp_AuthorVersion_0.pdf)); applying speculative execution + rollback to CUDA command streams (safe for deterministic kernels) is untouched territory, as is Infiniswap-style slab batching of memcpy-class traffic ([Infiniswap](https://www.usenix.org/system/files/conference/nsdi17/nsdi17-gu.pdf)).
4. **CXL inside the host, API-replay at the edge.** Use Panmnesia/Samsung-class CXL pooling to make one physical GPU serve many Vectant sessions economically ([Panmnesia](https://panmnesia.com/uploads/panmnesia-CXL-GPU.pdf)), while the client link stays API-level. No product composes the two planes.
5. **Driver-API-only forwarding (LUPINE's insight) with codegen-maintained coverage**, plus an honest capability ladder: full speed for async-heavy workloads, graceful degradation flags for sync-bound ones — published per-workload expectations instead of pretending uniform performance.

### (c) Ranked top-5 insights shaping Vectant architecture

1. **Intercept at the highest stable interface, forward to genuine drivers.** Library/API-level forwarding (rCUDA/Bitfusion/LUPINE lineage) avoids both ZLUDA's legal exposure and ExpEther's physics wall; on Windows, target the WDDM/dxg projection pattern Microsoft itself uses ([LWN](https://lwn.net/Articles/820950/)). Never emulate the bus; never reimplement the API.
2. **Design the wire protocol around persistent remote state, not per-call shipping.** Allocation handles minted once, uploads streamed once, steady-state traffic = small command batches — validated by rCUDA's dataset-proportional Ethernet collapse and Semeru/Infiniswap placement lessons. Remote VRAM tracking (alloc/residency/lifetime) is the core subsystem, exactly as the concept doc anticipates.
3. **Synchronization density, not bandwidth, predicts per-workload pain.** Publish a workload taxonomy (async compute = near-native; tight sync loops = degraded) and engineer batching/fencing to amortize RTTs — the single consistent finding across 15 years of literature ([survey](https://dl.acm.org/doi/10.1145/3068281), [GPUrpc](https://dl.acm.org/doi/10.1145/2950056)).
4. **Control plane ≠ data plane is proven doctrine — finish it.** Bitfusion failed partly because attachment required its hypervisor estate; LUPINE's hosted demo shows a bare data plane invites trust gaps. Vectant's rent/auth/route/bill layer with direct client↔host encrypted data path is the missing productization, and 55–60% fleet idleness ([HotNets'25](https://conferences.sigcomm.org/hotnets/2025/papers/hotnets25-final8.pdf)) is the market opening.
5. **Assume hostile environments: ECC-free GPUs, dropped packets, signed OSes.** DS-CUDA's redundancy, rCUDA's migration machinery, and the ZLUDA fallout together define the resilience checklist — session-level error detection, reconnectable state, and a legal posture that only forwards, never forks, vendor interfaces.
