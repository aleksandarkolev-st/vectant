# Lessons

- When a user provides logo or brand image assets, use the supplied files directly instead of recreating the artwork in SVG or code.
- For Next.js Docker builds, `NEXT_PUBLIC_*` values must be injected at build time; runtime compose env does not override values already baked into the client bundle from `.env.production`.
- `IncrementalCache` (`backend/synthi-webrtc-compiler/worker/src/hmr/incremental_cache.rs`) is hard-coded to write entries as `{key}.o` with default `0o644` perms — it is **object-file storage**, not generic artifact storage. Anything that needs to be `exec()`'d (e.g. `compile_runner`'s linked host_runner binary) MUST materialise the cached bytes to a real exec path with `+x` before returning; otherwise spawn fails with EACCES on the 2nd+ build (first build is a cache miss). When in doubt, add a `chmod` step at the consumer site or use a separate cache.
- When propagating errors across IPC/serialization boundaries (worker → log_dc → frontend), embed the root cause (errno / `io::ErrorKind` / file existence) directly in the `.context()` string. anyhow's source chain is dropped when only `error.to_string()` is serialized, leaving the frontend with a useless top-level message and no way to disambiguate ENOENT / EACCES / ETXTBSY / ENOMEM.
- The worker Dockerfile's Java install must be **full `openjdk-17-jdk`**, not `-headless`. The headless variant omits `libawt_xawt.so` and its X11 deps, which makes Java GUI apps die at `Toolkit.<clinit>` with `UnsatisfiedLinkError`. Setting `DISPLAY` + `-Djava.awt.headless=false` in the runner is necessary but not sufficient — the native lib has to be present in the image.
- `tokio::Child::kill().await` reaps the process but **does not wait for the X server to release that client's window resources** — that cleanup happens asynchronously once the kernel closes the socket and the X server processes the client disconnect, and matchbox-window-manager only drops its reparenting frames in response to the resulting DestroyNotify events. When the worker reuses Xvfb across rebuilds (Java GUI rerun, cpp HMR full-restart-with-reuse), the next JVM/runner can race against the dead client's still-mapped windows; the window-discovery code locks onto the OLD XID and GStreamer captures a black framebuffer. Wait via `xlsclients` client-count drop (bounded ≤1.5s) before spawning the replacement.
- `useCompiler().isCompiling` flips back to false the moment the worker emits `{stage: 'runner', status: 'done'}` — i.e. when the runner has **started**, not when the user's program exits. Don't gate run-state UI (Stop/Reload buttons in the TopNav) on `isCompiling` alone, because the build "completes" while the GUI is still alive. The page-level `isGuiRunning` (driven by `synthi:gui-start`/`gui-end`) is the durable signal for "program is alive"; combine them: `isRunning = isCompiling || isGuiRunning`. Note that hard `client.reconnect()` in stop/restart tears down the data channel that delivers `gui-end`, so handlers must also clear `isGuiRunning` synchronously as a backstop.
- The shipped runner's keyboard input path was SDL-only — `runner_bin.rs` would `SDL_PushEvent(SDL_KEYDOWN/UP)` keyed on the SDL keycode, which never reaches apps that read via `XNextEvent` directly (raw-Xlib code with `XSelectInput(KeyPressMask)` — e.g. the snake demo). Mouse worked because the mouse path already used `xtest_fake_input`. The fix: emit the X11 keysym alongside the SDL keycode from `main.rs::js_key_to_x11_keysym`, build a `keysym → keycode` reverse map from `get_keyboard_mapping` at runner startup, and inject a real `KeyPress`/`KeyRelease` (XTest event types 2/3) in addition to `SDL_PushEvent`. Don't replace the SDL path — SDL apps need it because SDL keycodes diverge from X11 keysyms for non-ASCII keys (the high 0x40000000 bit).
- `cancel-build` and `stop-runner` handlers in `main.rs` used to unconditionally `runner_store.take()` and kill Xvfb/GStreamer regardless of which session the request targeted. A stale cancel for a previous session (frontend can send these during reconnect/cleanup) would kill the shared Xvfb that the currently-live session was streaming through, producing `XIO: fatal IO error 110 (Connection timed out) on X server ":99"` in the live runner. Always gate the teardown on a session_id match against `RunnerState.session_id`; cancel-all (no session_id specified) is still allowed.
- When a UI surface can exist both as a floating popup and as a docked panel, do not drive both modes from one visibility boolean. Keep the popup state separate, then move/focus the docked instance through the layout store so navbar actions, activity-bar actions, and sidebar fallback behavior can stay consistent.
- For dense workspace chrome like the floating status island, prefer icon-only status affordances with a tooltip over text labels when the user wants a tighter layout; keep the icon colour as the live state signal instead of adding extra pills or words.
- For docking sidebar auto-collapse, keep transient collapse sizing on the split child wrapper, not just the inner tab group. If the wrapper keeps its original flex slot, the editor cannot reclaim the width and the animation reads as a fade instead of a real resize. Also use `IDE_PANEL` constants for sidebar-type checks so panel ID spelling stays aligned with the registry.
- In flex row splits, do not feed normalized fractions like `0.2` / `0.8` directly into `flex-grow` if one sibling can later collapse to `0`. When the remaining grow factors sum to less than `1`, the browser is allowed to leave the rest of the row as unused free space. Scale the weights up first (for example `size * 1000`) so a surviving pane still expands to fill the available width after collapse.
- When moving a tab strip into the navbar, remove the entire legacy host header row, not just the tab labels. Otherwise the old collaboration/status chrome leaves a blank secondary bar under the navbar. If you restore the old custom tab-strip scrollbar, give it its own lane below the tabs instead of overlaying the tab underline.
- For Monaco inside resizable dock layouts, `automaticLayout` plus custom dock events may still miss sidebar collapse timing. Observe the actual editor viewport with `ResizeObserver` and call `editor.layout()` on size changes; otherwise the code surface can visually shift while leaving stale blank space on the right.
- Do NOT declare a backgrounded command failed/blocked based on mid-flight probes. A slow first `git push` over HTTPS can take minutes; probing it with `git rev-parse @{upstream}` / `git ls-remote` while it's still uploading shows "no upstream / branch not on origin," which is NOT evidence of an auth block — it just hasn't finished. I wrongly told the user the push was "blocked on GitHub credential auth" and edited handoff docs to say so; the push had actually succeeded (`* [new branch] ... -> ...`, exit 0). Wait for the task-completion notification, then read the output file + `git rev-parse origin/<branch>` for ground truth before diagnosing. When retrying a possibly-stuck network git op, use `GIT_TERMINAL_PROMPT=0` so it fails fast instead of hanging.
- Do NOT run multiple heavy `docker build`s concurrently piped through `Select-Object -Last N` (or any buffering pipe). The pipe hides BuildKit progress until EOF, two big builds saturate the daemon (even `docker images` queues), and if a session reload orphans the tracked background tasks they appear to "run for hours" with zero output. Build one image at a time, foreground or background, with `--progress=plain` so output streams line-by-line and you can read the task `.output` file to see the exact current step. When debugging a "stuck" build, FIRST probe the daemon (`docker version`/`info` with a hard `timeout`) and check image `CreatedSince` — a healthy daemon + stale image means the build process died/hung, not the engine. The `@anthropic-ai/claude-code` global install is ~23s, not minutes.
- On Windows Git Bash, `docker exec -w /app ...` fails with "Cwd must be an absolute path" because MSYS rewrites `/app` into a Windows path. Prefix the command with `MSYS_NO_PATHCONV=1` (or use `//app`) for any docker flag that takes an absolute container path (`-w`, `-v` targets, `cp` dests).
- Bare `node --test` (no path args) in `backend/collab-server` **hangs with zero output** — its default discovery globs run extra `*.test.js` files, and one of them opens a handle (server/socket) that never exits, so the runner never reports and the process lingers. Always scope it: `node --test --test-timeout=20000 backend/collab-server/__tests__/*.test.js` (per-test timeout kills any individual hang; explicit paths avoid the runaway discovery). The collab-server suite is 55 `node:test` tests and finishes in ~3s when scoped. The tests use file-relative `require('../x')`, so run-from-repo-root is fine. If a run produces an empty `.output` file and node processes linger, it's a discovery/handle hang, not a slow suite — stop it (`TaskStop`) and re-scope rather than waiting.
- A branch that normalizes line endings (CRLF→LF) makes `git merge` report **whole files as one big conflict** even when the real semantic changes are tiny and disjoint. Don't hand-merge the inflated markers. Diagnose first: for each conflicted file compare stages ignoring whitespace/CR — `diff -w --strip-trailing-cr <(git show :2:f) <(git show :3:f)` (and `:1:` = base). If `theirs-vs-base` is 0, the other side only touched line endings → `git checkout --ours`. If both changed disjoint regions, LF-normalize the three stages (`git show :N:f | tr -d '\r'`) and let `git merge-file -p ours base theirs` 3-way-merge them cleanly (exit 0 = no real conflict); only the genuinely-overlapping hunks need manual resolution. This turned a 7-file "whole-file conflict" merge into 3 take-ours + 3 auto-merges + 1 small manual hunk.
- Shared branches (`dev`) drift: `origin/dev` can be **ahead of your local** with other people's commits. Before any push, `git fetch` then check **both** directions — `git log --oneline dev..origin/dev` (must be EMPTY for a clean fast-forward) and `origin/dev..dev` (what you'd add). If `dev..origin/dev` is non-empty, a plain push is rejected and `--force` would **delete their commits** — reconcile by **merging `origin/dev` in** (never force on a shared branch), resolve, verify, then push. In this session origin/dev had 9 cloud-deploy/GKE commits our local merge had never seen; force-pushing would have wiped the production-deploy line.
- After fast-forwarding a feature branch onto an updated `dev`, **re-read the actual files before trusting an earlier analysis** — a prior reconciliation here was built on the *pre-merge* versions and was materially wrong against reality (the worker pod runs `runAsUser:0`+priv-esc, not `drop ALL`; persistence is a **shared** `collab-data-pvc` + git/GCS, not per-workspace disks; there is **no GPU**; there is **no egress NetworkPolicy**). Grounding a design/plan on stale reads produces confident-but-fictional specs. Re-`Read` the current files on the current commit.
- Workflow/subagents share the account session limit and can **fail mid-run** ("You've hit your session limit"). Don't blind-retry (it re-throttles until reset). When *recon* subagents fail, do the recon yourself with `Read`/`Grep` — it's actually better, since it keeps the findings in the main context instead of a subagent transcript. Tag any conclusions that depended on the throttled (failed) research as explicitly **unvalidated** in the output rather than presenting assumptions as findings.
