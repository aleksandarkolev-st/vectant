# Lessons

- When a user provides logo or brand image assets, use the supplied files directly instead of recreating the artwork in SVG or code.
- For Next.js Docker builds, `NEXT_PUBLIC_*` values must be injected at build time; runtime compose env does not override values already baked into the client bundle from `.env.production`.
- `IncrementalCache` (`backend/synthi-webrtc-compiler/worker/src/hmr/incremental_cache.rs`) is hard-coded to write entries as `{key}.o` with default `0o644` perms — it is **object-file storage**, not generic artifact storage. Anything that needs to be `exec()`'d (e.g. `compile_runner`'s linked host_runner binary) MUST materialise the cached bytes to a real exec path with `+x` before returning; otherwise spawn fails with EACCES on the 2nd+ build (first build is a cache miss). When in doubt, add a `chmod` step at the consumer site or use a separate cache.
- When propagating errors across IPC/serialization boundaries (worker → log_dc → frontend), embed the root cause (errno / `io::ErrorKind` / file existence) directly in the `.context()` string. anyhow's source chain is dropped when only `error.to_string()` is serialized, leaving the frontend with a useless top-level message and no way to disambiguate ENOENT / EACCES / ETXTBSY / ENOMEM.
- The worker Dockerfile's Java install must be **full `openjdk-17-jdk`**, not `-headless`. The headless variant omits `libawt_xawt.so` and its X11 deps, which makes Java GUI apps die at `Toolkit.<clinit>` with `UnsatisfiedLinkError`. Setting `DISPLAY` + `-Djava.awt.headless=false` in the runner is necessary but not sufficient — the native lib has to be present in the image.
- `tokio::Child::kill().await` reaps the process but **does not wait for the X server to release that client's window resources** — that cleanup happens asynchronously once the kernel closes the socket and the X server processes the client disconnect, and matchbox-window-manager only drops its reparenting frames in response to the resulting DestroyNotify events. When the worker reuses Xvfb across rebuilds (Java GUI rerun, cpp HMR full-restart-with-reuse), the next JVM/runner can race against the dead client's still-mapped windows; the window-discovery code locks onto the OLD XID and GStreamer captures a black framebuffer. Wait via `xlsclients` client-count drop (bounded ≤1.5s) before spawning the replacement.
- `useCompiler().isCompiling` flips back to false the moment the worker emits `{stage: 'runner', status: 'done'}` — i.e. when the runner has **started**, not when the user's program exits. Don't gate run-state UI (Stop/Reload buttons in the TopNav) on `isCompiling` alone, because the build "completes" while the GUI is still alive. The page-level `isGuiRunning` (driven by `synthi:gui-start`/`gui-end`) is the durable signal for "program is alive"; combine them: `isRunning = isCompiling || isGuiRunning`. Note that hard `client.reconnect()` in stop/restart tears down the data channel that delivers `gui-end`, so handlers must also clear `isGuiRunning` synchronously as a backstop.
- The shipped runner's keyboard input path was SDL-only — `runner_bin.rs` would `SDL_PushEvent(SDL_KEYDOWN/UP)` keyed on the SDL keycode, which never reaches apps that read via `XNextEvent` directly (raw-Xlib code with `XSelectInput(KeyPressMask)` — e.g. the snake demo). Mouse worked because the mouse path already used `xtest_fake_input`. The fix: emit the X11 keysym alongside the SDL keycode from `main.rs::js_key_to_x11_keysym`, build a `keysym → keycode` reverse map from `get_keyboard_mapping` at runner startup, and inject a real `KeyPress`/`KeyRelease` (XTest event types 2/3) in addition to `SDL_PushEvent`. Don't replace the SDL path — SDL apps need it because SDL keycodes diverge from X11 keysyms for non-ASCII keys (the high 0x40000000 bit).
- `cancel-build` and `stop-runner` handlers in `main.rs` used to unconditionally `runner_store.take()` and kill Xvfb/GStreamer regardless of which session the request targeted. A stale cancel for a previous session (frontend can send these during reconnect/cleanup) would kill the shared Xvfb that the currently-live session was streaming through, producing `XIO: fatal IO error 110 (Connection timed out) on X server ":99"` in the live runner. Always gate the teardown on a session_id match against `RunnerState.session_id`; cancel-all (no session_id specified) is still allowed.
- When a UI surface can exist both as a floating popup and as a docked panel, do not drive both modes from one visibility boolean. Keep the popup state separate, then move/focus the docked instance through the layout store so navbar actions, activity-bar actions, and sidebar fallback behavior can stay consistent.
- For dense workspace chrome like the floating status island, prefer icon-only status affordances with a tooltip over text labels when the user wants a tighter layout; keep the icon colour as the live state signal instead of adding extra pills or words.
- For docking sidebar auto-collapse, keep transient collapse sizing on the split child wrapper, not just the inner tab group. If the wrapper keeps its original flex slot, the editor cannot reclaim the width and the animation reads as a fade instead of a real resize. Also use `IDE_PANEL` constants for sidebar-type checks so panel ID spelling stays aligned with the registry.
- In flex row splits, do not feed normalized fractions like `0.2` / `0.8` directly into `flex-grow` if one sibling can later collapse to `0`. When the remaining grow factors sum to less than `1`, the browser is allowed to leave the rest of the row as unused free space. Scale the weights up first (for example `size * 1000`) so a surviving pane still expands to fill the available width after collapse.
- When moving a tab strip into the navbar, remove the entire legacy host header row, not just the tab labels. Otherwise the old collaboration/status chrome leaves a blank secondary bar under the navbar. If you restore the old custom tab-strip scrollbar, give it its own lane below the tabs instead of overlaying the tab underline.
- For Monaco inside resizable dock layouts, `automaticLayout` plus custom dock events may still miss sidebar collapse timing. Observe the actual editor viewport with `ResizeObserver` and call `editor.layout()` on size changes; otherwise the code surface can visually shift while leaving stale blank space on the right.
- Do NOT declare a backgrounded command failed/blocked based on mid-flight probes. A slow first `git push` over HTTPS can take minutes; probing it with `git rev-parse @{upstream}` / `git ls-remote` while it's still uploading shows "no upstream / branch not on origin," which is NOT evidence of an auth block — it just hasn't finished. I wrongly told the user the push was "blocked on GitHub credential auth" and edited handoff docs to say so; the push had actually succeeded (`* [new branch] ... -> ...`, exit 0). Wait for the task-completion notification, then read the output file + `git rev-parse origin/<branch>` for ground truth before diagnosing. When retrying a possibly-stuck network git op, use `GIT_TERMINAL_PROMPT=0` so it fails fast instead of hanging.
- Do NOT run multiple heavy `docker build`s concurrently piped through `Select-Object -Last N` (or any buffering pipe). The pipe hides BuildKit progress until EOF, two big builds saturate the daemon (even `docker images` queues), and if a session reload orphans the tracked background tasks they appear to "run for hours" with zero output. Build one image at a time, foreground or background, with `--progress=plain` so output streams line-by-line and you can read the task `.output` file to see the exact current step. When debugging a "stuck" build, FIRST probe the daemon (`docker version`/`info` with a hard `timeout`) and check image `CreatedSince` — a healthy daemon + stale image means the build process died/hung, not the engine. The `@anthropic-ai/claude-code` global install is ~23s, not minutes.
- On Windows Git Bash, `docker exec -w /app ...` fails with "Cwd must be an absolute path" because MSYS rewrites `/app` into a Windows path. Prefix the command with `MSYS_NO_PATHCONV=1` (or use `//app`) for any docker flag that takes an absolute container path (`-w`, `-v` targets, `cp` dests).
- Bare `node --test` (no path args) in `backend/collab-server` **hangs with zero output** — its default discovery globs run extra `*.test.js` files, and one of them opens a handle (server/socket) that never exits, so the runner never reports and the process lingers. Always scope it: `node --test --test-timeout=20000 backend/collab-server/__tests__/*.test.js` (per-test timeout kills any individual hang; explicit paths avoid the runaway discovery). The collab-server suite is 55 `node:test` tests and finishes in ~3s when scoped. The tests use file-relative `require('../x')`, so run-from-repo-root is fine. If a run produces an empty `.output` file and node processes linger, it's a discovery/handle hang, not a slow suite — stop it (`TaskStop`) and re-scope rather than waiting.
- A branch that normalizes line endings (CRLF→LF) makes `git merge` report **whole files as one big conflict** even when the real semantic changes are tiny and disjoint. Don't hand-merge the inflated markers. Diagnose first: for each conflicted file compare stages ignoring whitespace/CR — `diff -w --strip-trailing-cr <(git show :2:f) <(git show :3:f)` (and `:1:` = base). If `theirs-vs-base` is 0, the other side only touched line endings → `git checkout --ours`. If both changed disjoint regions, LF-normalize the three stages (`git show :N:f | tr -d '\r'`) and let `git merge-file -p ours base theirs` 3-way-merge them cleanly (exit 0 = no real conflict); only the genuinely-overlapping hunks need manual resolution. This turned a 7-file "whole-file conflict" merge into 3 take-ours + 3 auto-merges + 1 small manual hunk.
- Shared branches (`dev`) drift: `origin/dev` can be **ahead of your local** with other people's commits. Before any push, `git fetch` then check **both** directions — `git log --oneline dev..origin/dev` (must be EMPTY for a clean fast-forward) and `origin/dev..dev` (what you'd add). If `dev..origin/dev` is non-empty, a plain push is rejected and `--force` would **delete their commits** — reconcile by **merging `origin/dev` in** (never force on a shared branch), resolve, verify, then push. In this session origin/dev had 9 cloud-deploy/GKE commits our local merge had never seen; force-pushing would have wiped the production-deploy line.
- After fast-forwarding a feature branch onto an updated `dev`, **re-read the actual files before trusting an earlier analysis** — a prior reconciliation here was built on the *pre-merge* versions and was materially wrong against reality (the worker pod runs `runAsUser:0`+priv-esc, not `drop ALL`; persistence is a **shared** `collab-data-pvc` + git/GCS, not per-workspace disks; there is **no GPU**; there is **no egress NetworkPolicy**). Grounding a design/plan on stale reads produces confident-but-fictional specs. Re-`Read` the current files on the current commit.
- Workflow/subagents share the account session limit and can **fail mid-run** ("You've hit your session limit"). Don't blind-retry (it re-throttles until reset). When *recon* subagents fail, do the recon yourself with `Read`/`Grep` — it's actually better, since it keeps the findings in the main context instead of a subagent transcript. Tag any conclusions that depended on the throttled (failed) research as explicitly **unvalidated** in the output rather than presenting assumptions as findings.
- PowerShell idempotency guards that **capture `gcloud` stdout into a variable** (`$exists = gcloud ... --format='value(name)'; if ($exists) {...}`) are unreliable when the script is run via `powershell -File` (esp. backgrounded): on this box `gcloud` resolves to `gcloud.ps1`, and the captured value came back **empty inside the `-File` child even when the resource existed**, so the `else`/create branch ran every time (a create was silently skipped on one run; a re-create attempted on another). It works fine when typed interactively, which masks the bug. **Fix:** detect existence by the **exit code** of `gcloud ... describe ... *> $null` + `if ($LASTEXITCODE -eq 0)`, never by captured stdout. Also: don't wrap native `gcloud` calls in `$ErrorActionPreference='Stop'` (its normal stderr status lines can derail flow); use `'Continue'` + explicit `$LASTEXITCODE` checks. And keep `throw`/`Write-Error` messages free of parenthesized text like `"(exit $LASTEXITCODE)"` — under `-File` it was parsed as a command and threw "term 'exit' is not recognized".
- Docker Desktop's Linux engine (`npipe:////./pipe/dockerDesktopLinuxEngine`) can be **down even though `docker version` worked minutes earlier** — `docker` then fails identically in foreground AND background (it's the daemon, not the run mode). For **registry→registry image re-hosting** (re-host a third-party image into Artifact Registry by digest), don't depend on the local daemon: use **`crane copy SRC DST`** (Google go-containerregistry, daemon-free) and auth to AR with `crane auth login <region>-docker.pkg.dev -u oauth2accesstoken -p (gcloud auth print-access-token)`. Pin the resulting **index digest** (`crane digest DST`) into the manifest. Download crane via `https://github.com/google/go-containerregistry/releases/latest/download/go-containerregistry_Windows_x86_64.tar.gz` + `tar -xzf`. NOTE: `docker` commands also fail when launched as a **detached background task** even if the daemon is up (named-pipe not reachable from the detached process) — run docker foreground.
- Docker Desktop on this box crashes its **WSL engine** (`exit status 0xc00000fd`, then `500 Internal Server Error` on every API call — taking the running dev stack down with it) under **C:-drive disk pressure**, NOT just the run-mode flakiness of #19/#27. C: ran to **0.7 GB free** and every heavy `docker`/`trivy` op destabilized the daemon. ALWAYS check **free space per drive** (`Get-Volume | ? DriveLetter`) before blaming Docker. For **image CVE scanning**: `docker scout` needs a Docker Hub login (unusable headless, exit 1 = the auth wall not a result); the **trivy CONTAINER** (`aquasec/trivy`) crashed the WSL VM (heavy DB download + scan); the fix is **host-native `trivy.exe`** (reads the image via the daemon API — lighter on the VM) with the DB + temp forced onto the roomy drive: `--cache-dir D:\trivy-cache` + `$env:TEMP/$env:TMP/$env:TMPDIR='D:\trivy-tmp'` (trivy DB is ~1.5 GB; first scan also extracts ~350 MB of layers to temp). Use `--skip-db-update` on retries (DB cached), `--timeout 9m` (layer analysis is slow under disk pressure), `--ignorefile` for documented waivers, `--exit-code 1` for the gate signal. dind/containerd bases DO carry CRITICALs (grpc/Go-stdlib in the bundled containerd + `kind`/`ctr` gobinaries) — bump the tool (e.g. `kind` to a release built with patched Go) where fixable, and `.trivyignore` the unfixable base-bundled ones with a justification + revisit-on-base-bump note.
- A failing runtime/sandbox is NOT proof of an upstream hard-block — **test the documented working pod-spec recipe before declaring defeat.** Sysbox **#1006** ("`mount through procfd: operation not permitted`" at sysfs mount, on a `runtimeClassName: sysbox-runc` pod) was diagnosed as an unfixable v0.7.0+containerd-2.x bug and **PARKED the whole Phase-2 substrate for 2 days**. The real cause was a one-line miss in the smoke pod: **no `hostUsers: false`** (k8s user-namespaces — REQUIRED for sysbox-runc via the containerd CRI path; needs k8s≥1.33 + containerd≥2.0.5). With it set, a non-privileged sysbox pod ran `docker run hello-world` on GKE (1.35.3 / containerd 2.1.5), `uid_map 0 41549824 65536` proving root-in-userns. Before assuming you need a custom/from-source build: (1) read the actual fix **PR** named in the issue thread (here sysbox-runc PR#106 = the `features` cmd) and (2) **inspect the released binary's real capability cluster-free** — `docker run --entrypoint sh <deploy-image> -c '<path>/sysbox-runc features'` showed v0.7.0 ALREADY shipped the fix, so the planned master-static build was unnecessary. A 2-min binary inspection + reading maintainer comments beat spinning infra or building from source. Our prod spec (`runtimePodSpec.js`) already set `hostUsers:false`; only the Slice-0 smoke test omitted it — so the "blocker" never affected the real code path.
- A "run a command in the workspace runtime" feature MUST route to the **Sysbox runtime pod**, not the managed-program/headless path. First cut of MCP `exec_in_runtime` reused the program-sessions `/exec-terminal` flow → `launchManagedSession` defaults `runtimeType:'cli'` → `programRuntimeTarget` returns **`headless`** (only `runtimeType:'container'` takes `sysbox-pod`). The headless PTY runs on the **collab-server host** (not the pod) with **DOCKER_HOST scrubbed** + a userId-keyed cwd — so `docker ...` can't work and a PAT's identity is wrong. Fix: a dedicated `runtimeExecOnce(runtimeScope, cmd)` (k8s-exec into the pod's `runtime` container) behind `POST /program-runtime/:slug/exec`, resolving `runtimeScope` via `pickRuntimeScopeForSlug(slug)` — **slug-routed, never userId**, which also dissolves the PAT→workspaceUserId problem. Lesson: when exposing "runs in the runtime," trace it all the way to `programRuntimeTarget` and confirm docker is actually present (the headless path is docker-less by design).
- PAT identity ≠ runtime filesystem identity. Auth is NextAuth **JWT strategy, no Prisma adapter**, so `session.user.id` (= `workspaceUserId`, which keys the per-user workspace dir / the `flushWorkspaceDocsToDisk` path) is the **OAuth provider id**, while `authenticatePat`/`resolveActor` yield the **Prisma `User.id`** (email lookup) — different values. So PAT-authed program **launch** is only safe for **container** programs (sysbox-pod path = slug-routed); cli/web programs (headless/hybrid) are userId-routed and need the deferred PAT→workspaceUserId resolution. Gate AI launch to `runtimeType:'container'`.
- KasmVNC (single-app kiosk image) gotchas, all found by building+running locally: (1) the basic-auth user store is **`~/.kasmpasswd`** (default), set non-interactively with `printf '%s\n%s\n\n' pw pw | kasmvncpasswd -u USER -rwo` (need `-rwo` = read+write+owner or vncserver prompts for a "user with write access"); (2) KasmVNC 1.4 added a DE picker — pass **`-select-de manual`** to vncserver so it uses your `~/.vnc/xstartup` instead of prompting; (3) KasmVNC **binds TLS at init** and needs a readable cert/key even for plain HTTP — the debian snakeoil key is group-only-readable by `ssl-cert`, so **generate an ephemeral self-signed pair owned by the run user** and point `kasmvnc.yaml` `network.ssl.{pem_certificate,pem_key}` at it with `require_ssl:false`; then it serves **plain HTTP** (curl `/` → 401 without creds, 200 with). Kiosk = `matchbox-window-manager -use_titlebar no` (no menu/panel) + `exec $APP_CMD` in xstartup (app-exit ends the session). Validate the security property by asserting `xterm`/browser/file-manager/DE binaries are ABSENT in the built image.
- `gcloud.ps1` can throw `System.OutOfMemoryException` **at launch** under host RAM pressure (Docker Desktop's WSL VM + a large `docker pull` had ballooned memory) — a *host* failure, not a GCP error (a lighter `gcloud ... list` moments later succeeded), and it left the target cluster **still RUNNING/billing** with an empty `$LASTEXITCODE`. For a long destructive op like `clusters delete`, use **`--quiet --async`** so gcloud submits the operation and exits immediately (tiny footprint) instead of holding a multi-minute polling process; then confirm via `clusters list` (`STOPPING` → gone). Free memory/disk first by `docker rmi`-ing large pulled images. Always check exit/status explicitly — an earlier teardown failure was masked the same way (#26).
- **Rootless dind does NOT run under Sysbox — use ROOTFUL `docker:dind`.** A `docker:dind-rootless`-based pod under `runtimeClassName: sysbox-runc` (+`hostUsers:false`, non-privileged) crash-loops at startup with `[rootlesskit:parent] error: failed to start the child: fork/exec /proc/self/exe: operation not permitted` (plus iptables/ip6_tables modprobe EPERM). Cause: rootlesskit tries to create ANOTHER user namespace nested inside the one Sysbox already provides, which the kernel blocks. Sysbox's whole model is "run a NORMAL (rootful) daemon — Sysbox supplies the userns isolation," so under Sysbox use rootful `docker:dind` (daemon at `/var/run/docker.sock`). Proven live on GKE: the IDENTICAL k8s Deployment (sysbox-runc + hostUsers:false + non-privileged + subPath PVC mount) crash-looped with the rootless image but reached Ready and ran `docker run hello-world` with rootful `docker:27-dind` — uid_map `0 <high-host-base> 65536` confirming root-in-userns (not host root). `dind-rootless` is for the Docker-Desktop `--privileged` hybrid (rootless-inside-privileged), NOT for Sysbox. Corollary: validate a runtime/sandbox image on the ACTUAL target runtime (Sysbox pod), not just locally — the privilege/userns model differs.
- **Recovering a wedged Docker Desktop (WSL engine 500s) under disk pressure + freeing its space.** When the host drive holding Docker's data fills up, the WSL engine crashes (500 on every API call) and does NOT recover via `wsl --shutdown` alone. Docker's images/build-cache live in a standalone **`docker_data.vhdx`** (here 57 GB) — find it by searching Docker's data dir, NOT via `Lxss` distro registration (the `docker-desktop` distro's own ext4.vhdx is tiny ~0.16 GB; the data disk is separate). On this box Docker Desktop was installed on **D:** (`D:\Docker\DockerDesktop\Docker Desktop.exe`; data `D:\Docker\wsl\disk\docker_data.vhdx`). With the daemon dead you can't `docker prune`, so the recovery that BOTH frees space AND un-wedges the engine: stop Docker (`Stop-Process 'Docker Desktop','com.docker.backend'` → `wsl --shutdown`) → **delete `docker_data.vhdx`** (regenerable image cache — NOT user data) → relaunch Docker Desktop → it recreates a fresh empty data disk + a healthy engine. Freed 57 GB + fixed the engine in one move. CAVEATS: (1) **Docker Desktop is a GUI app — it CANNOT be launched headlessly**; `Start-Process` from the agent context leaves no running process and the engine never comes up, so the USER must start it from their interactive session. (2) The harness blocks `Remove-Item` on **C:** system paths — target D: / explicit `-LiteralPath` subpaths. (3) Locate WSL vhdx via `Get-ItemProperty HKCU:\Software\Microsoft\Windows\CurrentVersion\Lxss\* | select DistributionName,BasePath`. (4) Always check **per-drive** free space (`Get-Volume`) — the full drive may be a data drive (D:), not C:.
- **GPU on GCP: regional QUOTA ≠ zonal hardware ≠ live capacity — check all three.** A region can show `NVIDIA_T4_GPUS` quota > 0 yet have **no T4 hardware in any zone** (europe-west10: quota 1, but `gcloud compute accelerator-types list --filter="zone:<z>"` was EMPTY for every zone — only RTX-PRO-6000 existed, in one zone). And even where hardware exists, a node-pool create can fail with **`GCE_STOCKOUT`** ("zone does not have enough resources") — europe-west1-b stocked out on T4 after a 35-min wait. Before planning GPU work: (1) `gcloud compute accelerator-types list --filter="name=<type>"` to find zones that actually HAVE the GPU (not just `regions describe` quota); (2) expect stockouts, try another zone/region (us-central1 has the deepest capacity); (3) a ZONAL cluster can only add pools in ITS zone, so trying a different zone means a new cluster. Tear the half-built cluster down immediately when a pool errors — the default pool still bills. Also: `gcloud ... | tail` masks the real exit/error — a stocked-out `node-pools create` printed "operation still running" and the pipe showed exit 0; check the operation: `gcloud container operations list --filter="targetLink~<cluster>"` → `statusMessage`.
- **A `podSelector{k8s-app:kube-dns}` egress rule BREAKS DNS on GKE clusters with NodeLocal DNSCache.** GKE enables NodeLocal DNSCache (`node-local-dns`) by default on many clusters: it's a **hostNetwork** DaemonSet that intercepts the kube-dns ClusterIP **on the node**, so the real DNS responder's identity is the NODE (host, in/around 10/8), not a pod labeled `k8s-app=kube-dns`. A NetworkPolicy egress rule that only allows DNS `to: podSelector{k8s-app:kube-dns}` therefore never matches the responder, and a cluster-internal-deny (egress-hardening's `except 10/8`) drops DNS entirely — runtime pods resolve nothing (validated live on Dataplane V2: public-by-IP worked, public-by-DNS timed out). Fix: allow **UDP/TCP :53 to ALL destinations** (a `ports`-only egress rule, no `to`). DNS-only (no other internal service listens on 53) and safe when public egress is already permitted, so it doesn't widen lateral movement. resolv.conf points at the kube-dns ClusterIP (e.g. 34.118.224.10) even though node-local-dns answers it.
- **GKE Dataplane V2 (Cilium) enforces ClusterIP egress by BACKEND-POD identity, not the service CIDR.** New GKE clusters use a non-RFC1918 service CIDR (`34.118.224.0/20`), which an egress `except` of [10/8, 172.16/12, 192.168/16, 169.254/16] does NOT cover — so you'd expect a lateral-movement gap to in-cluster Services. It does NOT exist on Dataplane V2: Cilium resolves ClusterIP traffic to the backend pod and evaluates policy against THAT identity (in 10/8), so kube-api `34.118.224.1:443` and other Services are correctly BLOCKED by the 10/8 deny (validated live). Do NOT add the service CIDR to the except list on Dataplane V2 — unnecessary and would over-allow. (On a non-identity-aware CNI / kube-proxy iptables this differs — re-validate there.)
- **GCP regional `SSD_TOTAL_GB` quota (default 500) is shared across ALL clusters in the region — a scratch cluster collides with prod's disks.** Creating the `sysbox-pool` (and later the workspace PVC) on a fresh scratch cluster in europe-west10 failed with `GCE_QUOTA_EXCEEDED: Quota 'SSD_TOTAL_GB' exceeded. Limit: 500.0` because prod `synthi-beta-cluster`'s 3 nodes + the scratch default-pool node already consumed ~490/500 GB. GKE node boot disks default to **pd-balanced**, which counts against `SSD_TOTAL_GB` (as does pd-ssd); the default `standard-rwo` StorageClass is pd-balanced too. `DISKS_TOTAL_GB` (pd-standard/HDD) was wide open (40/4096). Fix without a quota bump: create the scratch node pool with `--disk-type pd-standard --disk-size 50`, and put any scratch PVC on the legacy `standard` StorageClass (pd-standard) — both then bill against the roomy DISKS quota. Check headroom first: `gcloud compute regions describe <region> --flatten=quotas --format='table(quotas.metric,quotas.usage,quotas.limit)'`. CAVEATS: (1) a node-pool create that fails on quota leaves a **broken, node-less pool** behind — a retry hits `409 Already exists`, so `node-pools delete` it before recreating; (2) the task-level exit of a backgrounded `gcloud ... 2>&1 | tail; echo EXIT=$PIPESTATUS` reports the *pipeline* exit (0 from `echo`), masking gcloud's real failure — read the captured `EXIT=` line. For the runtime pod itself, `/var/lib/docker` is ephemeral emptyDir on the node disk unless `RUNTIME_PERSIST_DOCKER_DATA` is set, so a small workspace PVC is plenty for validation.
- **After a merge that adds Prisma migrations, the local dev Postgres silently drifts → P2022 → 500s on every route touching the changed tables.** The local DB lives in a persistent `postgres-data` volume and was created with **`prisma db push`** (no `_prisma_migrations` tracking — `prisma migrate status` reports ALL migrations "not applied" even though the tables exist). A merge that adds columns (e.g. `WorkspaceMembership.invitedByEmail` from `20260612110000_workspace_membership_roles`) updates `schema.prisma` + the route code, but the running DB never gets the column, so `prisma.*` calls throw `PrismaClientKnownRequestError` **P2022 `The column … does not exist`**. The browser only shows opaque `500`s across many routes (marketplace, installed, program-sessions, integrations, members) — the real error is in the **frontend container log**, not the console. There is **no local auto-migrate step** (prod applies migrations via `synthi/Dockerfile.migrate` as a K8s Job) — so add `db push` to the post-merge / `docker compose` rebuild checklist. - **Proving Sysbox userns isolation: use `/proc/self/uid_map`, NOT `docker info`.** When validating a dind-under-Sysbox runtime pod, `docker info --format '{{.SecurityOptions}}'` does NOT list `name=userns` (it shows `seccomp` + `cgroupns`) — because the user namespace is provided by **Sysbox at the POD boundary** (`hostUsers:false` + `runtimeClassName: sysbox-runc`), not by the inner dockerd remapping. The authoritative proof of root-in-userns is `kubectl exec <pod> -- cat /proc/self/uid_map` → `0 <high-host-base> 65536` (e.g. `0 2387148800 65536`): container uid 0 maps to an unprivileged host uid, so root-in-pod ≠ host root. The `k8s/sysbox/README.md` C1 step ("`docker info ...` # expect name=userns") is misleading for the dind case — uid_map is the real signal. Also: the per-workspace dockerd really does listen on TCP **2376** inside the pod (confirmed via `/proc/net/tcp`), which is exactly why `recomputeRuntimeScopePorts` must filter it ([[lessons]] infra-port filter / RUNTIME_INFRA_PORTS).
